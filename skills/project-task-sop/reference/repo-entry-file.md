# 仓库入口文件（AGENTS.md 等）— 通用规范

> 适用：任何需要让"不知道本项目的 agent"进门就知道去哪看、按任务该读什么的仓库。
> 本文件不含项目信息，是纯机制说明。具体内容由各项目在自己的 manifest + 维度里写。

## 1. 它是什么，不是什么

| 是 | 不是 |
|---|---|
| 入口：纪律指向、按任务读维度、维护契约 | 规则库：正文、环境事实、凭据、命令全串 |
| 生成物：生成区由 `sop.py entry` 从 manifest 渲染 | 手写稿：生成区手改必被覆盖 |
| 稳定的：不含日期、不含"最近变更" | 流水账：进展、状态补充应落 `ai/status/` |

**判据一句话**：入口里每一条信息，都应该能回答"这条我是从哪个维度抄来的"；答不上来就说明它该写在维度里，入口只留指向。

## 2. 三种入口形态，按场景选

| 形态 | 位置 | 适用 | 代价 |
|---|---|---|---|
| **仓根入口** | `codeRoot/AGENTS.md`（`entry.file = "AGENTS.md"`） | 代码仓会被 Codex/Claude/IDE 打开，且 `ai/` 与仓库同源（或已在库内） | 与维度体系分离，`sop.py audit` 扫不到，必须靠 `entry --check` 兜底；`ai/` 不进版本库时对 clone 者是断链 |
| **工作目录入口** | 与 `ai/` **同级**（`entry.file = "../AGENTS.md"`） | agent 以项目目录（`ai/` 的父目录）为主工作目录 | 仓库外人看不到；只能做指路（细则在维度），否则成第三份事实源 |
| **薄壳 + 全量并存** | 仓根一份薄壳 + ai 同级一份全量 | 既要仓库可读、又要本机全套路由 | 两份要各守预算，且同一句话只能出现在一处 |
| **无入口** | — | 单次任务、无跨会话价值 | 每次会话都要口头贴上下文 |

两种入口可以并存，但**每个目录只允许一份**，且都只做指路。

## 2.1 落点决策门（生成前必问）

`python sop.py entry` 的默认落点是 `codeRoot/<entry.file>`，**默认值不是决策**。生成前必须由人确认落点（三选一），结论写进 `plan.md` 的 `assumptions` 或 NOTES 决策点。

| 判据（按顺序问） | 结论 |
|---|---|
| `ai/` 是否随仓库进版本库？ | 不进 → **优先与 `ai/` 同级**（仓根入口会指向 clone 者看不到的 `ai/context`） |
| 谁会以**仓库**为工作目录打开它（Codex / IDE / 协作者 clone）？ | 会 → 仓根也要有一份（可以是薄壳，指向上面的全量入口） |
| 项目是 monorepo / 子项目结构？ | 落点写到**实际被打开的那个目录**（相对 `codeRoot` 的路径），不要一律顶到仓库根 |
| 以上都不成立（纯本机单会话） | 不启用 `entry`（`file` 留空），别为一次性任务造入口 |

**询问话术（照抄即可）**：

> 入口 `AGENTS.md` 放哪？① 仓库根（clone 者可见，但 `ai/` 不在库里会断链）；② 与 `ai/` 同级（路径最稳，仓库外人看不到）；③ 指定其他目录（子项目根等）。

工具会打印 `entry 落点: <路径>（仓库内/仓库外…）` 提醒这一行；当 `ai/` 在仓库外而落点仍在仓库内时，还会额外提示「clone 者看不到 ai/context」——那是提示，不是替你决定。

## 3. 启用步骤（先定落点，再 3 步配置）

0. **定落点**（§2.1 的三选一）：`file` 写成相对 `codeRoot` 的路径——仓根写 `AGENTS.md`，与 `ai/` 同级写 `../AGENTS.md`，其他目录按实际层级写。

1. manifest 增加 `entry`（`file` 为空 = 不启用，对既有项目零影响）：

   ```json
   "entry": {"file": "AGENTS.md", "maxLines": 45, "title": "仓库入口（AGENTS.md）"}
   ```

2. 在需要"出现在入口纪律清单里"的维度上补 `entryHint`（**一条 ≤1 行**，写"什么时候必须注意什么"，不写具体值/路径/命令）：

   ```json
   {"id": 8, "key": "dev-workflow", "title": "开发工作流与环境",
    "entryHint": "本机默认工具链可能不是构建所需版本，先核对再构建"}
   ```

3. `python sop.py entry` 生成；之后每次改 manifest 或 `entryHint` 都重跑一次，`python sop.py entry --check` 做校验。

## 4. 生成区 / 手写区分工

```
<!-- ENTRY-GEN:BEGIN -->       ← 工具重写：纪律索引 + 任务→维度路由表 + 维护契约
<!-- ENTRY-GEN:END -->
<!-- ENTRY-MANUAL:BEGIN -->    ← 项目手写：架构概览、易踩空点、上游资产边界、协作约定
<!-- ENTRY-MANUAL:END -->
```

- 生成区内容全部来自 manifest（维度 `entryHint` + `tasks`），改它等于改错地方。
- 手写区只放**只能人判断**的内容；能被维度事实覆盖的，一律搬回维度。
- 目标文件已存在但没有 `ENTRY-GEN` 标记时，工具**拒绝改动**并提示两种做法（手工插标记 / 确认后 `--force` 覆盖）。

## 5. `entry --check` 的 5 条 lint

| 检查 | 为什么 |
|---|---|
| 行数 ≤ `maxLines` | 入口一长就退化成第二份文档，必然漂移 |
| 含「权威在 `ai/context`」声明 | 防止后来者把入口当权威 |
| 禁凭据关键词 / token 串 / 私钥块 | 入口文件常被提交进 git，泄密代价最高 |
| 禁绝对家目录路径（`C:\Users\…`、`/Users/…`） | 换机器即失效，且暴露个人信息 |
| 禁时效性状态词（"最近变更/状态补充/最新进展/本周"） | 流水账该进 `ai/status/`，否则每改一次就要手维护一次 |

超长行（>400 字符）也会告警——通常是"把维度正文整段抄进来"的信号。
`check --context` 会在启用 entry 的项目里顺带跑同一套 lint，只告警不阻塞。

## 6. 常见反模式

1. **入口当规则库**：把 5 条硬规则的全套推断过程、命令串、表清单都抄进入口 → 维度一改入口就旧，且没人发现（入口不在 `audit` 覆盖范围）。
2. **入口手写 + 只有一份**：没有生成区，改维度时想不起来同步入口。用 `entryHint` 让入口跟着 manifest 走，成本最低。
3. **`entryHint` 写成项目事实**：写"JDK 路径是 X"这种会变的值。正确写法是"构建前先核对 JDK 版本（详见维度 N）"。
4. **多份入口各写一半**：仓根一份、工作目录一份、README 再一份。判据：同一句话只在一个目录出现，其余只放链接。

## 7. 迁移已有入口文件的检查表

- [ ] 逐条问"这条出自哪个维度"→ 答不出的搬进对应维度，入口换成一句 `entryHint`
- [ ] 入口里的环境事实（路径、凭据、端口、库连接）**全部**下移到 `dev-workflow` 类维度
- [ ] 入口里的任务进展/状态 → 移到 `ai/status/`
- [ ] 加上 `ENTRY-GEN` / `ENTRY-MANUAL` 标记，跑 `python sop.py entry --check`
- [ ] 行数落在 `maxLines` 内；超了就说明还在做第二事实源
